# Specification & Overview

### 1. Scope & Objective
- **Source:** `docs/plans/0.1.0-follow-up/0.1.0-follow-up.md`
- **Goal:** Make repository mutations update branch-history and canvas state immediately, and make branch synchronization data complete and reliable across refreshes.
- **In-Scope:**
  - Complete the existing full repository refresh path after checkout, fetch, pull, and push operations before reporting success.
  - Calculate, persist, and consume local-branch ahead/behind counts for branches with upstreams, together with `is_head` and latest commit metadata.
  - Define behavior for branches without upstreams, missing upstream references, and repositories with no local branches.
  - Add frontend, Rust, and canvas hydration regression coverage using existing Vitest and Rust test helpers.
  - Run the required frontend, Rust, and Tauri smoke validation and regenerate affected generated architecture documentation.
- **Out-of-Scope:** Merge, rebase, cherry-pick, stash, worktree, branch rename/delete, and advanced conflict-resolution workflows.

### 2. Technical Constraints & Architecture
- Reuse the existing refresh coordination in `src-tauri/src/manager.rs` and `src-tauri/src/refresh.rs`; do not depend on filesystem watcher timing for mutation correctness.
- The Git mutation entry points are in `src-tauri/src/git.rs`: `execute_git_checkout`, `git_fetch_operation`, `git_pull_operation`, and `git_push_operation`.
- Preserve current Git error behavior while surfacing refresh failures instead of returning misleading success.
- Use `git2` for ahead/behind calculation and persist the results in `cached_git_branches` alongside existing branch metadata.
- Prefer existing Vitest and Rust test helpers. Do not add end-to-end infrastructure unless existing test boundaries cannot verify the required contracts.
- The known Windows Rust test-binary launcher issue means `cargo check` is the required Rust validation fallback when focused Rust tests cannot launch successfully.
- Any generated architecture, IPC, state, component, test, or database documentation changed by implementation must be regenerated rather than hand-edited.

### 3. Dependencies, Risks, Assumptions & Open Decisions
- **Dependencies:** Existing repository refresh coordination, Git operation error handling, `git2`, `cached_git_branches`, dashboard/repository-detail/canvas consumers, existing Vitest and Rust test helpers, and the Tauri desktop runtime.
- **Risks:** A refresh failure could be hidden behind a successful Git mutation; branch states without valid upstream references may produce ambiguous synchronization values; watcher-triggered and explicit refreshes may race or duplicate work; generated documentation may become stale after cross-layer changes.
- **Assumptions:** The existing refresh path is the authoritative way to rebuild repository history and branch state; existing consumers already have fields or indicators for the refreshed branch metadata; database schema changes are not required unless repository inspection proves otherwise.
- **Resolved Decisions:** Checkout will use a manager-aware backend command that wraps the existing low-level checkout helper and awaits the authoritative full refresh. Mutation success means the backend cache transaction completed and the workspace invalidation event was queued or emitted; frontend hydration remains asynchronous and is verified through event-driven coverage. A configured but missing upstream is persisted as unavailable (`has_upstream = 0`, ahead/behind counts reset to zero) and recorded in refresh diagnostics. Repositories with no local branches reconcile successfully as an empty snapshot; unborn branches fail with a clear refresh error. Focused Rust test launchability and the minimum generated documentation set remain execution-time verification items rather than behavior decisions.

## Resolved Decision Register

* **d1-checkout:** Use a manager-aware checkout command that wraps the existing low-level checkout helper, because the current checkout command lacks `path_id`, database, and refresh-writer inputs.
* **d2-success:** Define mutation success as completed backend full-cache refresh plus queued or emitted workspace invalidation. Frontend hydration is asynchronous and is covered by event-driven tests.
* **d3-upstream:** Treat a configured but missing upstream as unavailable: persist `has_upstream = 0` and zero counts, and record a refresh diagnostic rather than presenting the branch as synchronized.
* **d4-empty-repo:** Allow repositories with no local branches to reconcile successfully as an empty snapshot; reject unborn branches with a clear refresh error.

These decisions resolve the implementation blockers identified in the adversarial review. Focused Rust test launchability and the affected generated-documentation set remain validation findings to establish during execution, not unresolved product or architecture choices.
